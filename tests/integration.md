# TESTS: Integration (end-to-end)

## Роль

Сквозные тесты через полный конвейер: интерфейс → сессия → парсер → движок → проекция → логи → сборщик промпта → лестница → валидатор → рендерер. В отличие от юнит-тестов в спецификациях, здесь проверяется не поведение компонента, а **совместное** поведение.

Три режима (см. `ARCHITECTURE.md` §5): `no-llm` (A), `llm` (B), `broken-llm` (C). Режим A — обязательный baseline.

## Золотой путь (15 команд)

Используется во всех режимах. Источник — спецификация шага 1 (сюжет №4).

| # | Команда | Ожидаемое состояние после | Ожидаемый код |
|---|---|---|---|
| 1 | `осмотреться` | без изменений, видна фляга | `ok` |
| 2 | `идти на восток` | `loc_market` | `ok` |
| 3 | `осмотреться` | видны раненый, торговец, фильтр, фонарь | `ok` |
| 4 | `поговорить с раненым про фильтры` | без изменений | `ok` |
| 5 | `поговорить с торговцем про код` | без изменений, отказ | `condition_not_met` |
| 6 | `взять фонарь` | фонарь в инвентаре | `ok` |
| 7 | `бросить фонарь` | фонарь обратно на рынке | `ok` |
| 8 | `идти на запад` | `loc_shelter` | `ok` |
| 9 | `взять флягу` | фляга в инвентаре | `ok` |
| 10 | `идти на восток` | `loc_market` | `ok` |
| 11 | `использовать флягу на раненого` | фляга исчезла, фильтр +1, `wounded_watered=true` | `ok` |

## Негативные сценарии (7 команд, отдельная сессия)

Подаются в отдельной сессии (не смешиваются с золотым путём).

| # | Команда | Ожидание |
|---|---|---|
| N-1 | `идти вверх` в убежище | `no_exit`, локация та же |
| N-2 | `идти на север` на рынке до кода | `locked`, локация `loc_market` |
| N-3 | `взять фильтр` после того, как оба взяты | `no_item_here` |
| N-4 | `бросить флягу` до взятия | `not_in_inventory` |
| N-5 | `поговорить с торговцем про флягу` | `no_topic` |
| N-6 | `использовать фонарь на дверь` | `invalid_combination` |
| N-7 | `поговорить с раненым про код` в убежище | `no_npc_here` |

Плюс два сценария для проверки интерфейса/парсера:
- N-8: `абракадабра` → `unknown`, `skip_reason=unknown_command`, клиент LLM не вызван.
- N-9: пустая строка → `unknown`.

## Проверки, применяемые ко всем режимам

| # | Проверка | Как проверяется |
|---|---|---|
| C-1 | Золотой путь проходится (все 15 ходов) | все `Outcome` из лога имеют ожидаемые коды |
| C-2 | Финальная проекция = эталон | сравнение с эталоном (ниже) |
| C-3 | `game_finished = true` | из `TurnResult` последнего хода |
| C-4 | Все тексты непустые | `final_text` не пуст, без `{` |
| C-5 | Нет утечки механики в текст | grep по флагам и кодам причин в `final_text` |
| C-6 | `session.jsonl` консистентен | каждый `turn` имеет парный `presentation` |
| C-7 | `save` + `load` восстанавливают проекцию | сравнение побайтово |
| C-8 | Нет `aborted` | `TurnResult.aborted = false` на всех ходах |
| C-9 | Нет `rung=4` | из `diagnostic.jsonl` |

## Эталон финальной проекции

После золотого пути в любом режиме:

```
location:        loc_bunker
game_won:        true
bunker_door_open: true
has_code:        true
wounded_watered: true
inventory:       {item_code: 1}
item_placement:
  loc_shelter:   {}
  loc_market:    {}    # фляга отдана, фильтры отданы, фонарь убран и возвращён?
                       # ВНИМАНИЕ: фонарь взят и брошен на рынке → он снова на рынке
  loc_bunker:    {}
npc_locations:   {npc_wounded: loc_market, npc_trader: loc_market}
turn:            15
```

**Уточнение по фонарю:** шаги 6–7 берут и бросают фонарь, значит после шага 7 он снова на рынке. В финальной проекции `item_placement[loc_market][item_lamp] = 1`.

## Режим A: `no-llm`

**Запуск:** клиент LLM = `null`.

| # | Проверка | Ожидание |
|---|---|---|
| E-A-1 | Золотой путь | C-1..C-9, все `rung=3` |
| E-A-2 | Негативные сценарии | корректные коды, состояние не испорчено, `UNKNOWN` не идёт в LLM |
| E-A-3 | `save`/`load` после золотого пути | проекция идентична |

**E-A — обязательный baseline.** Если E-A-1 красный — E-B и E-C не запускаются. Проблема не в LLM.

## Режим B: `llm`

**Запуск:** реальный клиент LLM.

| # | Проверка | Ожидание |
|---|---|---|
| E-B-1 | Золотой путь | C-1..C-9, финальная проекция = эталон |
| E-B-2 | Негативные сценарии | коды как в A, тексты валидны |
| E-B-3 | Распределение `rung` | **собирается**, порог не задаётся (см. ниже) |
| E-B-4 | Список ходов с `rung > 1` | выгружается с причинами для ручного анализа |

**Пороги не задаются.** Шаг 16 собирает цифры, шаг 17 (живая сессия) решает, хорошие ли они. E-B не ставится в CI (зависит от модели), запускается вручную перед релизом; сравнивается отчёт с предыдущим запуском — регрессия по метрикам, а не «прошло/не прошло».

## Режим C: `broken-llm`

**Запуск:** мок-клиент с детерминированной инъекцией отказов. Инъекция привязана к номеру хода в сессии.

| Ход | Инжекция | Ожидание |
|---|---|---|
| 1 | Таймаут 1-й, валидный 2-й | `rung=2`, во 2-м промпте **нет** заметки |
| 2 | Невалидный 1-й (выдуманное имя), валидный 2-й | `rung=2`, во 2-м промпте **есть** заметка с `reason.message` |
| 3 | Таймаут оба | `rung=3`, `fallback_reason=timeout_twice` |
| 4 | 4xx 1-й | `rung=3`, `skip_reason=config_error`, клиент вызван 1 раз |
| 5 | Пустой 1-й, валидный 2-й | `rung=2` (пустой = невалидный) |
| 6 | Невалидный оба (выдуманное число) | `rung=3`, `fallback_reason=validation_failed_twice` |
| 7–15 | Норма | `rung=1` |

| # | Проверка | Ожидание |
|---|---|---|
| E-C-1 | Золотой путь | C-1..C-9, `rung` по сценарию, нет `aborted`/`rung=4` |
| E-C-2 | Сверка с A **на каждом ходу** | проекция после хода N совпадает с A для всех N=1..15 |
| E-C-3 | `save`/`load` | проекция восстанавливается идентично |

**E-C-2 — ключевая проверка.** Не только финальная проекция, а каждый ход. Ловит «сбой на ходу 3 изменил состояние, но к ходу 15 всё сошлось».

**Уточнение по ходу 4:** на ходу 4 золотого пути — `TALK раненый «фильтры»`, `reason_code=ok`, `response_text` задан. При `rung=3` рендерер берёт `response_text` (canon выше шаблона). Ожидаемый текст — «У меня есть один, но мне нужна вода.»

**Уточнение по ходу 6:** `TAKE фонарь`, `reason_code=ok`, `response_text=null`. При `rung=3` рендерер берёт `specific[TAKE][ok]` с `{item}` = «Сломанный фонарь».

Тот же финал, другой порядок действий. Проверяет, что проходимость не зависит от конкретного порядка, если он логически эквивалентен.

Вариант: игрок берёт фильтр с земли до похода за флягой (шаг 9 переставлен).

| # | Команда | Ожидание |
|---|---|---|
| 1 | `идти на восток` | `loc_market` |
| 2 | `взять фильтр` | фильтр в инвентаре |
| 3 | `идти на запад` | `loc_shelter` |
| 4 | `взять флягу` | фляга в инвентаре |
| 5 | `идти на восток` | `loc_market` |
| 6 | `использовать флягу на раненого` | фильтр +1 (=2), `wounded_watered=true` |
| 7 | `поговорить с торговцем про код` | фильтры списаны, код в инвентаре |
| 8 | `использовать код на дверь` | `bunker_door_open=true` |

Финальная проекция: то же, что эталон, кроме `item_lamp` (не тронут → лежит на рынке) и `turn=9` вместо `15`.

| # | Проверка | Ожидание |
|---|---|---|
| E-VAR-1 | Финальное состояние (с учётом отличий) | `game_won=true`, локация `loc_bunker` |

| # | Сценарий | Ожидание |
|---|---|---|
| E-SL-1 | Save после хода 5, load, продолжить с 6 | финал = эталон, `turn` корректен |

## Метрики прогона

Собираются в JSON-отчёт, плюс человекочитаемая сводка.

**По каждому режиму:**
- Число ходов.
- Распределение `rung` (1/2/3/4).
- Распределение `skip_reason` (unknown_command, config_error).
- Распределение `fallback_reason` (validation_failed_twice, timeout_twice, mixed, config_error, build_error).
- Число вызовов клиента (суммарно и в среднем на ход).
- Токены (prompt/completion), если провайдер вернул.
- Latency: mean, p50, p95, max.
- Распределение `reason_code` из `Outcome`.
- Отказы валидатора по кодам (`unknown_name`, `unknown_number`, `mechanics_leak`, `too_short`, `too_long`, `empty`).

**Только режим C:**
- Сверка с A на каждом ходу: результат (match / mismatch с указанием хода).
- `aborted` = 0.
- `rung=4` = 0.

**Только режим B:**
- Список ходов с `rung > 1` и причинами.
- Примеры отклонённых ответов (из `diagnostic.jsonl`).

## Порядок запуска

1. **E-A-1** (золотой путь, `no-llm`). Если красный — стоп.
2. **E-A-2** (негативные, `no-llm`).
3. **E-A-3** (save/load).
4. **E-C-1..3** (golden, broken-llm).
5. **E-VAR** (в A и C).
6. **E-SL-1..6**.
7. **E-B-1..4** (вручную).

## Известные ограничения

- E-B не детерминирован; «регрессия» определяется сравнением метрик, а не булевым результатом.
- Эталон финальной проекции зависит от канона; при изменении канона эталон обновляется.
- Replay несовместим с другим каноном; это не проверяется автоматически в MVP.
- Сценарий инжекции в режиме C привязан к номеру хода; при изменении золотого пути (например, добавлении команд) сценарий нужно пересмотреть.
