# SPEC: Loaders (canon + templates)

## Роль

Два загрузчика: канона и шаблонов. Оба читают YAML, валидируют и возвращают **иммутабельные** структуры в память. Загрузчик канона запускается первым; загрузчик шаблонов — вторым (ему нужен `reason_codes` из канона).

Оба работают **до** создания сессии. Если любой упал — сессия не создаётся, игра не запускается.

## Контракт

```
load_canon(path) -> Canon   # падает с CanonError при любой ошибке
load_templates(path, reason_codes: set[str]) -> Templates   # падает с TemplatesError
```

`CanonError` / `TemplatesError` содержат:
- `errors: [str]` — список всех найденных ошибок (собираемых) или одна (фатальная);
- каждая ошибка — с **путём в файле** (`locations[id=loc_market].exits[direction=north].to`) и коротким объяснением.

## Загрузчик канона: порядок фаз

Порядок жёсткий, подчинён зависимостям.

### Фаза 1. Разбор и форма (фатальная)

- YAML парсится. Синтаксическая ошибка — стоп, с номером строки.
- `meta.schema_version` = 1. Несовпадение — стоп.
- Присутствуют все обязательные секции: `meta`, `initial_state`, `flags`, `locations`, `npcs`, `items`, `use_targets`, `verbs`, `directions`, `reason_codes`, `win_condition`. Пустая секция (например, `npcs: []`) допустима.
- `meta.start_location` — строка.

### Фаза 2. Реестры и уникальность id

Собрать индексы: `{id: entity}` по локациям, NPC, типам предметов, флагам, кодам причин, направлениям, `use_targets`, темам внутри каждого NPC, глаголам.

- id внутри каждого пространства имён уникальны.
- id непустые, формат `[a-z][a-z0-9_]*`.
- темы внутри одного NPC уникальны.

### Фаза 3. Валидация реестров

- Флаги: `type` ∈ {`bool`, `number`}, `description` непустое.
- `initial_state.flags`: каждому объявленному флагу задано значение; нет значений для необъявленных.
- `reason_codes`: `ok` и `unknown` присутствуют; дубликатов нет.
- `verbs`: у каждого глагола ≥1 алиас; каждый аргумент ∈ {`direction`, `item`, `npc`, `topic`, `target`}; алиасы глаголов не пересекаются между глаголами.
- `directions`: `name` непустое; у каждого направления ≥1 алиас.
- `use_targets`: `name` непустое, ≥1 алиас.

### Фаза 4. Ссылочная целостность

- Каждый `exit.to` — существующая локация.
- Каждый `exit.direction` — в реестре направлений.
- Каждый `entity` в локации — либо id типа предмета, либо id NPC (ровно одно).
- Каждый NPC появляется **ровно в одной** локации через `entities`. Ноль — ошибка. Два — ошибка.
- Каждый `use_target.exit` (если задан) разрешается в существующий выход (`location` + `direction`).
- Каждый `use[].target` — либо id NPC, либо id `use_target`, либо id типа предмета.
- Каждое `condition`/`effect` — из закрытого набора (`flag` / `inventory_count`; `set_flag` / `add_to_inventory` / `remove_from_inventory`); аргументы (флаг, предмет) разрешаются.
- `win_condition` ссылается только на объявленные флаги.

### Фаза 5. Семантика

- **Достижимость локаций:** обход графа от `start_location` по всем выходам, игнорируя условия. Недостижимая локация — предупреждение.
- **Открываемость замков:** для каждого условия на выходе «флаг = true» есть хотя бы один эффект `set_flag` с этим флагом и `value=true`. Нет — **ошибка** (дверь без ключа).
- **Открываемость победы:** флаг из `win_condition` кем-то ставится. Нет — ошибка.
- **Живость типов предметов:** у каждого типа есть хотя бы один экземпляр в `entities` **или** его создаёт `add_to_inventory`. Нет — ошибка.

### Фаза 6. Перекрёстная согласованность

- Для каждого `use_target` с `exit`: хотя бы один эффект хотя бы одного USE-правила на этот `use_target` ставит в `true` флаг, который проверяет условие связанного выхода (если условие есть). Нет — **ошибка** (дверь и ключ разъехались).
- Имена сущностей (локации, NPC, типы предметов, `use_targets`) уникальны. Дубликаты — предупреждение (для валидатора прозы неоднозначность).

## Загрузчик шаблонов: проверки (фатальные)

- Для каждого `reason_code` из канона есть непустой `generic[code]`.
- Для каждой пары `(verb, ok)`, не входящей в `canon_guarantee`, есть непустой `specific[verb][ok]`.
- Каждый вариант любого шаблона — непустая строка.
- Все слоты в шаблонах ∈ {`item`, `npc`, `target`, `direction`, `topic`, `scene`, `response`, `response_on_fail`}.
- `{scene}` используется только в `specific.LOOK.ok`.
- Варианты одного шаблона различимы.
- **`generic`-шаблоны не содержат слотов** (слоты только в `specific`).
- Мультиглагольные коды (`no_npc_here`, `not_in_inventory`, `condition_not_met`) имеют `generic`; отсутствие `specific` для конкретного глагола — предупреждение, не ошибка.

## Известные ограничения

- Проверка «эффект существует» не проверяет, что он **достижим** при каких-то условиях. Полная разрешимость — планировщик, вне MVP.
- Проверка согласованности `use_target` ↔ `exit` ловит только случай «условие на выходе, а USE не ставит флаг». Обратный случай (USE ставит флаг, но на выходе его никто не проверяет) — легально (флаг может быть информационным, как `has_code`).
