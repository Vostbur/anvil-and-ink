# CANON_AUTHORING.md

Инструкция по созданию и расширению канона для Anvil and Ink.

Канон — это данные мира. Он не содержит кода логики, но полностью определяет, какие сущности существуют, где они находятся, какие действия возможны, какие условия проверяются и какие изменения применяются.

Основной принцип:

> Канон описывает наблюдаемый мир и допустимые правила. Движок исполняет их детерминированно. Рассказчик только украшает уже произошедшее.

---

## Когда менять канон

Меняйте канон, если живая сессия показала:

- игрок не понимает, куда идти;
- игрок не понимает, какой предмет нужен;
- NPC не даёт достаточной подсказки;
- дверь или механизм не объяснены;
- в мире нет объекта, который игрок логично пытается использовать;
- тема разговора сформулирована неестественно;
- fallback-тексты выглядят бедно, потому что в каноне мало наблюдаемых деталей.

Не меняйте канон сразу, если:

- это единичная странно сформулированная команда одного игрока;
- проблема явно в парсере и требует общего правила;
- проблема в LLM-промпте или валидаторе;
- изменение сломает золотой путь и автотесты без явного обновления эталонов.

По протоколу живых сессий: минимум три сессии перед существенными изменениями. Точечные объективные правки допустимы раньше.

## Файлы канона

Для MVP используются:

- `canon.yaml` — мир;
- `templates.yaml` — fallback-тексты.

Для нового мира лучше создать копию:

    my_world.canon.yaml
    my_world.templates.yaml

Запуск с новым каноном:

    python scripts/live_session.py --mode no-llm --canon my_world.canon.yaml --templates my_world.templates.yaml

или с LLM:

    python scripts/live_session.py --mode llm --canon my_world.canon.yaml --templates my_world.templates.yaml

## Общие правила

### ID сущностей

ID должны быть:

- стабильными;
- машинными;
- в `snake_case`;
- на латинице;
- уникальными внутри своего реестра.

Хорошо:

    loc_shelter
    item_flask
    npc_wounded
    exit_north_market

Плохо:

    Убежище
    Фляга
    1
    door-north

ID не показываются игроку. Их не должен видеть LLM в финальном тексте.

### Имена для игрока

Поле `name` — человеческое имя сущности. Оно может быть на русском.

Хорошо:

    name: "Раненый у входа"
    name: "Фляга воды"
    name: "Дверь в бункер"

Важно: парсер умеет искать отдельные значимые слова из многословных имён. Например, из «Раненый у входа» можно найти «раненый», из «Дверь в бункер» — «дверь» или «бункер».

Короткие слова длиной 2 символа и меньше не используются как отдельные кандидаты, чтобы не ловить предлоги и союзы.

### Наблюдаемость

Всё, что写入 в `description`, `response`, `response_on_fail`, должно быть наблюдаемым из позиции игрока.

Нельзя писать в каноническом тексте:

    flag bunker_door_open = true
    reason_code locked
    inventory_count item_filter >= 2

Можно писать:

    На двери мигает кодовый замок.
    Торговец жадно смотрит на фильтры в твоих руках.
    Раненый едва дышит и указывает на флягу.

### Механика vs нарратив

Движок знает механику. Игрок и LLM должны видеть только последствия и наблюдаемые признаки.

Плохо:

    response: "Флаг wounded_watered установлен."

Хорошо:

    response: "Раненый жадно пьёт и протягивает вам фильтр."

## Структура канона schema v1

Минимальный верхний уровень:

    meta:
      schema_version: 1
      title: "Название мира"
      start_location: loc_start
      note: "Краткое описание назначения канона."

    initial_state:
      location: loc_start
      stats:
        hp: 10
      inventory: {}
      flags:
        some_flag: false

    flags:
      some_flag:
        type: bool
        description: "Служебное описание флага для разработки."

    locations:
      loc_start:
        name: "Старт"
        description: "..."
        exits:
          - direction: east
            to: loc_next
        entities:
          - item_something

    npcs: {}
    use_targets: {}
    items: {}
    verbs: {}
    directions: {}
    reason_codes: {}
    win_condition:
      type: flag
      flag: game_won
      equals: true

---

## `meta`

Поля:

- `schema_version`: версия схемы. Для MVP — `1`.
- `title`: название мира.
- `start_location`: ID стартовой локации.
- `note`: произвольная заметка для разработчиков.

Стартовая локация обязана существовать в `locations`.

---

## `initial_state`

Определяет состояние игры до первого хода.

Поля:

- `location`: стартовая локация;
- `stats`: начальная статистика, например `hp`;
- `inventory`: начальное состояние инвентаря, обычно `{}`;
- `flags`: все булевы флаги, которые используются в мире.

Правило:

> Любой флаг, который проверяется или устанавливается в каноне, должен быть инициализирован в `initial_state.flags`.

Пример:

    initial_state:
      location: loc_shelter
      stats:
        hp: 10
      inventory: {}
      flags:
        bunker_door_open: false
        has_code: false
        wounded_watered: false
        game_won: false

---

## `flags`

Реестр флагов.

Для MVP ожидается булев тип:

    flags:
      bunker_door_open:
        type: bool
        description: "Дверь в бункер разблокирована."

Флаги — это внутреннее состояние. Они не должны попадать в текст игрока.

Описание флага нужно для разработчиков, тестов и диагностики, но не для нарратора.

---

## `locations`

Локации — узлы графа мира.

Структура:

    locations:
      loc_market:
        name: "Рынок"
        description: "..."
        exits:
          - direction: west
            to: loc_shelter
          - direction: north
            to: loc_bunker
            condition:
              type: flag
              flag: bunker_door_open
              equals: true
            effects:
              - type: set_flag
                flag: game_won
                value: true
        entities:
          - npc_wounded
          - npc_trader
          - item_filter
          - item_lamp

### Правила локаций

- `name` — отображаемое имя.
- `description` — наблюдаемое описание сцены.
- `exits` — выходы из локации.
- `entities` — кто и что изначально находится в локации.

В `entities` могут быть:

- ID предметов;
- ID NPC.

Предметы в `entities` размещаются в локации. NPC в `entities` привязываются к локации.

Не дублируйте размещение NPC в самом NPC. В MVP у NPC нет поля `location`. Где NPC стоит — определяется только `entities` локации.

### Описание локации

`description` должен решать игровые задачи:

- где я;
- что вокруг;
- куда можно идти;
- что можно заметить;
- какой механизм важен.

Для MVP настоятельно рекомендуется включать навигационные подсказки, потому что у игрока нет миникарты.

Хорошо:

    description: "Бетонная коробка, тусклая лампа, на полу — фляга; на восток — выход, других выходов нет."

Хорошо:

    description: >
      Ржавые контейнеры, у стены сидит раненый, за прилавком — торговец,
      на земле валяется фильтр и сломанный фонарь; на запад — обратно в убежище,
      на север — тяжёлая дверь с кодовым замком.

Важный приём: пишите подсказки в одном предложении через точку с запятую или точку с запятой, чтобы они не терялись при усечении блока `SCENE` до первого предложения.

### Выходы

Выход:

    exits:
      - direction: east
        to: loc_market

Поля:

- `direction`: ID направления из `directions`.
- `to`: ID локации назначения.

Условие выхода:

    condition:
      type: flag
      flag: bunker_door_open
      equals: true

Эффекты выхода:

    effects:
      - type: set_flag
        flag: game_won
        value: true

Для MVP движение между локациями происходит автоматически при успешном `GO`. В `effects` выхода указывайте только дополнительные изменения, например победу.

## `directions`

Реестр направлений.

Пример:

    directions:
      east:
        name: "восток"
        aliases:
          - "восток"
          - "на восток"
      west:
        name: "запад"
        aliases:
          - "запад"
          - "на запад"
      north:
        name: "север"
        aliases:
          - "север"
          - "на север"
      south:
        name: "юг"
        aliases:
          - "юг"
          - "на юг"

Правила:

- ID направления — короткий латинский: `east`, `north`.
- `name` — именительный падеж.
- `aliases` должны покрывать частые формы ввода.

Полезно добавлять:

    "на восток"
    "восток"
    "на север"
    "север"

Если хотите поддерживать «пойти налево», нужно либо добавлять направление `left` и маппить его в мировую сторону, либо расширять парсер. В MVP базовая модель — стороны света.

---

## `items`

Предметы.

Пример простого предмета:

    items:
      item_filter:
        name: "Фильтр"
        takeable: true
        use: []

Пример предмета с применением:

    item_flask:
      name: "Фляга воды"
      takeable: true
      use:
        - target: npc_wounded
          condition:
            type: flag
            flag: wounded_watered
            equals: false
          effects:
            - type: remove_from_inventory
              item: item_flask
              count: 1
            - type: add_to_inventory
              item: item_filter
              count: 1
            - type: set_flag
              flag: wounded_watered
              value: true
          response: "Раненый жадно пьёт и протягивает вам фильтр."
          response_on_fail: "Он уже напился воды."

### Поля предмета

- `name`: отображаемое имя.
- `takeable`: можно ли взять.
- `use`: список правил применения.

Если `use: []`, предмет существует, но ни на что не применяется. Это нормально для ложных предметов или декораций.

### Правила `use`

Структура:

    use:
      - target: <npc_id | item_id | use_target_id>
        condition:
          ...
        effects:
          ...
        response: "..."
        response_on_fail: "..."

Поля:

- `target`: на что применяется предмет.
- `condition`: необязательное условие успеха.
- `effects`: что происходит при успехе.
- `response`: текст успеха.
- `response_on_fail`: текст провала, если условие не выполнено или комбинация недопустима.

Целью `target` могут быть:

- NPC: `npc_wounded`;
- предмет: например, использовать ключ на замок, если замок представлен предметом;
- use_target: `exit_north_market`.

Для дверей и выходов лучше использовать `use_targets`, а не сами локации.

### Примитивы эффектов

Для MVP используются примитивы:

    type: set_flag
    flag: some_flag
    value: true

    type: add_to_inventory
    item: item_code
    count: 1

    type: remove_from_inventory
    item: item_filter
    count: 2

    type: add_to_location
    item: item_lamp
    count: 1
    to: loc_market

    type: remove_from_location
    item: item_flask
    count: 1
    to: loc_shelter

    type: change_location
    to: loc_bunker

Важно:

- `set_flag` скрыт от нарратора в дельтах, но может влиять на текст через `response`.
- `change_location` обычно применяется движком для `GO`; в ручных effects использовать только если спецификация это допускает.
- Все ID предметов и флагов должны существовать.
- `count` должен быть положительным целым.

## `npcs`

NPC — персонажи, с которыми можно говорить.

Пример:

    npcs:
      npc_wounded:
        name: "Раненый у входа"
        topics:
          - key: "фильтры"
            response: "У меня есть один, но мне нужна вода."
          - key: "код"
            response: "Торговец знает. Спроси у него."

      npc_trader:
        name: "Торговец"
        topics:
          - key: "код"
            condition:
              type: inventory_count
              item: item_filter
              min: 2
            response: "Держи. Не потеряй."
            response_on_fail: "Принеси два фильтра — и код твой."
            effects:
              - type: remove_from_inventory
                item: item_filter
                count: 2
              - type: add_to_inventory
                item: item_code
                count: 1
              - type: set_flag
                flag: has_code
                value: true

### Правила NPC

- NPC не хранит свою локацию. Его размещение — в `entities` локации.
- NPC не хранит `held_items` в MVP. Если NPC что-то выдаёт, это описано через эффекты USE или TALK.
- Темы — короткие ключи, которые игрок может произнести.
- `response` — текст успеха.
- `response_on_fail` — текст, если условие не выполнено.
- `effects` применяются только при успехе.

### Темы

Тема:

    topics:
      - key: "код"
        response: "..."

Ключ темы должен быть тем, что игрок реально напишет:

    спросить торговца про код
    поговорить с раненым про фильтры

Парсер поддерживает substring matching для тем, поэтому фраза:

    спросить торговца про код от двери

может разрешиться в тему `код`, если ключ `код` существует.

Хорошие ключи тем:

    вода
    фильтр
    фильтры
    код
    дверь
    бункер
    торговец
    раненый

Избегайте слишком длинных ключей, если ожидаете естественный ввод. Лучше:

    key: "код"

чем:

    key: "код от двери в бункер"

### Информационные темы

Тема может не иметь эффектов. Это нормально.

Пример:

    - key: "состояние"
      response: "Мне нужно воды. И фильтр."

Такой ход возвращает `ok`, но `applied` пуст. Это информационный TALK.

## `use_targets`

Специальные цели применения. Нужны, когда предмет используется не на NPC и не на обычный предмет, а на дверь, механизм, выход или структуру мира.

Пример:

    use_targets:
      exit_north_market:
        name: "Дверь в бункер"
        aliases:
          - "дверь"
          - "дверь в бункер"
          - "дверь на севере"
        exit:
          location: loc_market
          direction: north

Поля:

- `name`: отображаемое имя цели.
- `aliases`: формы, которыми игрок может назвать цель.
- `exit`: структурная ссылка на выход.

Используйте `use_targets` для:

- дверей;
- кодовых замков;
- рычагов, если они привязаны к выходу;
- механизмов, открывающих переход.

Для предмета `item_code`:

    item_code:
      name: "Код"
      takeable: true
      use:
        - target: exit_north_market
          effects:
            - type: set_flag
              flag: bunker_door_open
              value: true
          response: "Замок щёлкает, дверь приоткрывается."

После этого выход на север в `loc_market` становится проходимым, если его условие проверяет флаг `bunker_door_open`.

## `verbs`

Реестр глаголов парсера.

MVP поддерживает базовые глаголы:

    GO
    LOOK
    TAKE
    DROP
    TALK
    USE

Пример:

    verbs:
      GO:
        aliases:
          - "идти"
          - "пойти"
          - "в"
          - "на"
          - "к"
        args:
          - direction

      LOOK:
        aliases:
          - "осмотреть"
          - "оглядеться"
          - "смотреть"
        args: []

      TAKE:
        aliases:
          - "взять"
          - "поднять"
          - "подобрать"
        args:
          - item

      DROP:
        aliases:
          - "бросить"
          - "оставить"
          - "выложить"
        args:
          - item

      TALK:
        aliases:
          - "говорить"
          - "поговорить"
          - "спросить"
        args:
          - npc
          - topic

      USE:
        aliases:
          - "использовать"
          - "применить"
          - "открыть"
        args:
          - item
          - target

### Правила глаголов

- ID глагола — верхний регистр, латиница.
- `aliases` — то, что пишет игрок.
- `args` — типы аргументов, которые ожидает парсер.

Допустимые типы аргументов в MVP:

    direction
    item
    npc
    topic
    target

### Русская морфология

Парсер использует эвристики: нормализацию, fuzzy, стемминг, substring matching. Это помогает, но не делает парсер полноценным морфологическим анализатором.

При добавлении алиасов ориентируйтесь на частые формы:

    взять
    поднять
    подобрать

    говорить
    поговорить
    спросить

    использовать
    применить
    открыть

Если игроки массово пишут «дать», «отдать», «предложить», это может быть кандидат на новый алиас или на расширение грамматики. Но одно единичное наблюдение — не повод переписывать парсер.

Важно: текущая грамматика `USE` ожидает структуру примерно:

    использовать <предмет> на <цель>
    применить <предмет> к <цели>

Свободный порядок:

    дать раненому флягу

не является простой правкой канона. Для него нужно менять парсер и, возможно, спецификацию.

## `reason_codes`

Реестр причин, которые возвращает движок.

Пример:

    reason_codes:
      ok: "Действие выполнено"
      no_exit: "Такого выхода нет"
      locked: "Выход заперт"
      no_item_here: "Здесь нет такого предмета"
      not_takeable: "Это нельзя взять"
      not_in_inventory: "Этого нет в инвентаре"
      no_npc_here: "Здесь нет такого собеседника"
      no_topic: "Собеседник не хочет говорить на эту тему"
      condition_not_met: "Условие не выполнено"
      no_target: "Такой цели нет"
      target_not_here: "Цель находится в другом месте"
      invalid_combination: "Так это применить нельзя"
      unknown: "Команда не распознана"

Правила:

- Каждый `reason_code`, который может вернуть движок, должен быть здесь.
- Текст описания используется для промпта и fallback, но не должен буквально泄漏иться в финальный текст как машинный код.
- При добавлении новой причины нужно обновить:
  - движок;
  - спецификации;
  - templates;
  - тесты.

Для автора канона обычно достаточно использовать существующие причины. Новая причина — это изменение движка, а не только данных.

## `win_condition`

Условие победы.

Для MVP:

    win_condition:
      type: flag
      flag: game_won
      equals: true

Это значит: игра завершается победой, когда флаг `game_won` становится `true`.

Флаг `game_won` должен быть инициализирован в `initial_state.flags`.

## Templates

`templates.yaml` отвечает за fallback-тексты, когда LLM недоступен, отклонён или превысил бюджет ожиданий.

Основные требования:

- Каждый используемый глагол должен иметь шаблон.
- Каждый используемый `reason_code` должен иметь шаблон.
- Шаблоны не должны показывать ID, флаги, машинные причины или внутренние счётчики.
- Шаблоны должны быть согласованы с движком: если ход завершился `locked`, текст должен говорить о запертости, а не о отсутствии предмета.
- Шаблоны могут быть проще LLM, но не должны ломать погружение грубыми техническими фразами.

При добавлении нового канона:

1. Откройте существующий `templates.yaml`.
2. Убедитесь, что все `reason_codes` из вашего канона покрыты.
3. Убедитесь, что все `verbs` покрыты.
4. При необходимости добавьте варианты для новых локаций/предметов, если шаблоны используют слоты описания.
5. Запустите `no-llm` и проверьте тексты вручную.

Если вы добавляете новый `reason_code` в движок, без обновления templates игра может уйти в аварийную заглушку или показать сырую причину. Это баг контракта.

## Пошаговый рецепт нового канона

### 1. Нарисуйте граф мира

Перед YAML определите:

- локации;
- связи между ними;
- предметы;
- NPC;
- флаги;
- условие победы.

Пример простой структуры:

    loc_room
      item_key
      exit east -> loc_corridor

    loc_corridor
      npc_guard
      exit west -> loc_room
      exit north -> loc_exit
        condition: has_key

Победа:

    игрок попал в loc_exit
    flag game_won = true

### 2. Заполните `meta` и `initial_state`

Укажите стартовую локацию и все флаги.

### 3. Добавьте локации

Для каждой локации:

-Give ей понятное `name`.
- Напишите `description` с наблюдаемыми подсказками.
- Перечислите `exits`.
- Положите начальные предметы и NPC в `entities`.

### 4. Добавьте предметы

Для каждого предмета решите:

- можно ли его взять;
- можно ли его бросить;
- на что он применяется;
- какие эффекты он даёт;
- что говорит мир при успехе;
- что говорит мир при провале.

### 5. Добавьте NPC

Для каждого NPC:

- разместите его в локации;
- дайте темы;
- решите, какие темы информационные, а какие механические;
- добавьте условия и эффекты, если NPC отдаёт предмет или открывает доступ.

### 6. Добавьте use_targets

Если есть дверь, замок, механизм, связанный с выходом, создайте `use_targets`.

### 7. Проверьте verbs и directions

Убедитесь, что игрок может сказать основные действия естественно:

    осмотреться
    идти на восток
    взять ключ
    говорить с охранником про выход
    использовать ключ на дверь

### 8. Проверьте reason_codes

Все возможные провалы должны иметь понятные причины:

    no_exit
    locked
    no_item_here
    not_in_inventory
    no_npc_here
    no_topic
    condition_not_met
    invalid_combination

### 9. Обновите templates

Добавьте fallback-тексты для всех новых причин и глаголов.

### 10. Прогоните в `no-llm`

    python scripts/live_session.py --mode no-llm --canon my_world.canon.yaml --templates my_world.templates.yaml

Проверьте:

- игрок понимает, куда идти;
- предметы берутся;
- NPC отвечают;
- двери открываются;
- победа наступает;
- тексты не содержат мусора.

### 11. Прогоните негативные сценарии

Попробуйте команды, которые должны падать:

    идти вверх
    взять несуществующий предмет
    использовать предмет не туда
    говорить с NPC, которого нет
    говорить на тему, которой нет
    открыть дверь без ключа

Убедитесь, что причины и тексты адекватны.

### 12. Только потом включайте LLM

    python bench_ollama.py
    python scripts/live_session.py --mode llm --canon my_world.canon.yaml --templates my_world.templates.yaml

Смотрите диагностику:

- сколько ходов `rung=1`;
- сколько `rung=2`;
- сколько `rung=3`;
- есть ли `timeout_or_network`;
- есть ли `validation_failed_twice`.

## Как делать подсказки, не ломая загадку

Хорошая подсказка — наблюдаемая деталь, а не прямая инструкция.

Плохо:

    description: "Чтобы пройти дальше, найдите код и используйте его на двери."

Это слишком директивно и может быть воспринято как UI-подсказка.

Лучше:

    description: "На северной стене — тяжёлая дверь с кодовым замком. Рядом пусто."

Или:

    response: "Торговец смотрит на ваши фильтры и молча постукивает по кодовому замку."

Так игрок получает информацию, но сам строит гипотезу.

## Как тестировать парсер для нового канона

Парсер зависит от имён, алиасов и тем. После изменения канона проверьте типичные фразы.

### GO

    идти на восток
    пойти на восток
    на восток
    в восток

Если нужно поддерживать «выйти», добавляйте алиас осторожно: «выйти» может означать и выход из локации, и использование двери.

### LOOK

    осмотреться
    осмотреть
    оглядеться
    посмотреть

Если игрок пишет «где я?», это пока `UNKNOWN`. Чтобы улучшить опыт, можно:

- добавить алиас, если парсер это поддержит;
- сделать стартовое описание более явным;
- принять это как ограничение MVP.

### TAKE

    взять флягу
    поднять флягу
    подобрать флягу
    взять флягу воды

Для многословных имён важно, чтобы ключевое слово было длиной больше 2 символов.

### TALK

    говорить с торговцем
    поговорить с торговцем
    спросить торговца
    спросить торговца про код
    поговорить с раненым про фильтры

Тема должна быть указана через предлог:

    про
    о
    об
    насчет

Если игрок пишет «спросить торговца как открыть дверь», тема не будет распознана, если в каноне нет подходящего ключа. Лучше иметь тему:

    key: "дверь"

или:

    key: "выход"

но тогда нужно продумать, что NPC отвечает.

### USE

    использовать флягу на раненого
    применить флягу к раненому
    использовать код на дверь
    открыть дверь кодом

Текущий парсер лучше всего работает с конструкциями:

    использовать <item> на <target>
    применить <item> к <target>

Конструкции с двойным объектом:

    дать раненому флягу

пока не являются штатными для MVP. Если это массовый паттерн у игроков, это задача для расширения парсера, а не только канона.

## Частые ошибки при расширении канона

### Предмет описан, но не размещён

Ошибка:

    items:
      item_key: ...

Но ни в одной локации нет:

    entities:
      - item_key

Игрок не сможет его взять.

### NPC описан, но не размещён

Ошибка: NPC есть в `npcs`, но нет в `entities` локации.

Игрок не сможет с ним говорить.

### Флаг используется, но не инициализирован

Ошибка: условие проверяет `has_key`, но в `initial_state.flags` нет `has_key`.

Это может привести к непредсказуемому поведению или ошибке загрузки.

### Новый reason_code добавлен в канон, но нет шаблона

Игрок может увидеть аварийный текст или сырую причину.

Нужно обновить `templates.yaml`.

### Слишком длинное имя темы

Ошибка:

    key: "как открыть дверь в бункер"

Игрок напишет:

    спросить торговца про код

и не попадёт.

Лучше короткие темы и несколько тем при необходимости.

### Описание содержит то, чего нет в манифесте

После D-83 слова из описания локации добавляются в разрешённые имена. Но всё равно старайтесь не вставлять в описание случайные канонные имена других локаций, если это не нужно. Иначе LLM может начать смешивать сцены.

### LLM придумывает детали

Это не всегда баг канона. Часто это ограничение валидатора: он не проверяет смысл.

Что можно сделать:

- ужесточить промпт;
- сократить данные хода;
- добавить в описание больше точных наблюдаемых деталей;
- снизить температуру;
- использовать более послушную модель;
- принять часть галлюцинаций как цену атмосферности, если они не ломают факты.

## Минимальный чеклист перед коммитом нового канона

- [ ] Все ID уникальны.
- [ ] Все `to` в выходах существуют.
- [ ] Все `direction` в выходах существуют в `directions`.
- [ ] Все `entities` существуют в `items` или `npcs`.
- [ ] Все флаги в условиях и эффектах объявлены в `flags`.
- [ ] Все флаги инициализированы в `initial_state.flags`.
- [ ] Все `target` в `use` существуют как NPC, предмет или use_target.
- [ ] Все use_target корректно ссылаются на существующий выход.
- [ ] Все `reason_code` объявлены.
- [ ] Templates покрывают используемые глаголы и причины.
- [ ] `pytest -q` зелёный, если канон влияет на существующие тесты.
- [ ] Прогон `no-llm` вручную успешен.
- [ ] Негативные сценарии дают понятные отказы.
- [ ] При изменении MVP-канона обновлены эталоны интеграционных тестов.

## Рекомендации по размеру мира

Для Уровня 1 лучше маленький, но ясный мир.

Хороший размер:

- 2–4 локации;
- 3–6 предметов;
- 1–2 NPC;
- 1 главная цепочка;
- 1–2 ложных предмета;
- 3–5 флагов.

Не стоит сразу делать:

- большие города;
- сложную инвентарную экономику;
- множество побочных квестов;
- свободную боевую систему;
- сложные диалоги с ветвлением.

Сначала проверьте, что базовый конвейер выдерживает живого игрока.

## Как понимать связь канона и живых сессий

Канон — не просто данные. Это инструмент обучения игрока.

Если игрок massово пишет:

    где выход?
    куда идти?
    осмотреть дверь
    как открыть дверь

значит, мир недостаточно объясняет affordances.

Если игрок massово пишет:

    дать раненому флягу
    отдать флягу
    напоить раненого

значит, natural language expectation расходится с грамматикой парсера. Это может быть:

- пробел парсера;
- ограничение MVP;
- сигнал, что нужен более свободный parser layer.

Если LLM massово галлюцинирует:

    фляга пустая
    вы входите в локацию, где уже были
    торговец дал код без условий

значит, нужно смотреть промпт, манифест, валидатор и качество модели.

Канон может помочь, но не всегда является корнем проблемы.
