# PROMPT для нового чата

Скопируйте этот файл целиком в начало нового чата. Он даёт контекст для продолжения разработки: написание кода по готовым спецификациям, либо развитие проекта после шага 17.

---

Ты продолжаешь работу над проектом **`anvil-and-ink`** — текстовой приключенческой игрой на архитектуре «жёсткий движок + мягкий рассказчик» (Уровень 1). Спецификации готовы, кода ещё нет (или есть частично — см. `README.md`).

## Что прочитать в первую очередь

1. **`README.md`** — что за проект, в каком состоянии, что дальше.
2. **`ARCHITECTURE.md`** — сквозные контракты (`Command`, `Outcome`, `Manifest`, `TurnResult`, `Event`, `GameState`), карта компонентов, гарантии порядка. **Без этого нельзя писать ни один компонент.**
3. **`DECISIONS.md`** — 60 решений с обоснованием. Читать по мере необходимости; при вопросах «почему так» — искать здесь.
4. **`canon.yaml`** и **`templates.yaml`** — данные мира. Парсер, движок, шаблоны, загрузчик — все читают их.
5. **`specs/*.md`** — по одному файлу на компонент. Каждый начинается с секции «Контракт» со ссылкой на `ARCHITECTURE.md` и заканчивается юнит-тестами.
6. **`tests/integration.md`** — сквозные тесты (золотой путь, негативные сценарии, три режима, save/load).

## Порядок написания кода

Строго по `ARCHITECTURE.md` §8:

1. `specs/loaders.md` — загрузчик канона и шаблонов.
2. `specs/projection.md` — проекция состояния + event sourcing.
3. `specs/parser.md` — парсер команд.
4. `specs/engine.md` — движок правил.
5. `specs/templates_renderer.md` — рендерер шаблонов.
6. `specs/prompt_builder.md` — сборщик промпта + манифест.
7. `specs/validator.md` — валидатор прозы.
8. `specs/llm_ladder.md` — клиент LLM + лестница отката.
9. `specs/session.md` — оркестратор хода.
10. `specs/interface.md` — CLI.
11. `tests/integration.md` — интеграционные тесты.

Каждый шаг пишется и тестируется **независимо**: контракты зафиксированы, компоненты видят друг друга только через них. Не переходи к следующему шагу, пока юнит-тесты текущего не зелёные.

## Правила

- **Язык:** Python 3.11+. Типизация через `dataclasses` и `typing`. Без внешних фреймворков, кроме: `pyyaml` (канон), `pytest` (тесты), `httpx` или `requests` (LLM-клиент). Fuzzy-сравнение — `rapidfuzz` (если нужен; иначе — свой Левенштейн).
- **Никакой игровой логики в не-своих местах.** Парсер не проверяет предусловия, движок не разрешает слова, сессия не содержит правил. Если появляется соблазн — перечитать `ARCHITECTURE.md` §2.
- **Тесты — часть спецификации.** Каждая спецификация заканчивается таблицей тестов. Тест пишется **вместе** с кодом, не после. Красный тест — стоп.
- **Не расширять закрытые наборы** (эффекты, условия, глаголы, коды причин) без явного решения. Расширение — осознанная операция, см. `DECISIONS.md` D-08.
- **Логи:** два файла, `session.jsonl` (сейв) и `diagnostic.jsonl` (телеметрия). Не смешивать. `final_text` — только в `presentation`-записи.
- **Гарантии порядка** (`ARCHITECTURE.md` §4) — нерушимы. Состояние меняется до вызова LLM, `turn`-событие пишется до вызова LLM, fallback доступен всегда. Если рефакторинг нарушает любую — это баг.
- **Ошибки загрузчиков** — собираемые (полный список) или фатальные (стоп). Каждая с путём в файле. См. `specs/loaders.md`.
- **Комментарии в коде** — только для неочевидного. Имена — говорящие. Ссылки на `DECISIONS.md` (например, `# D-04: takeable: true`) приветствуются в местах, где решение не очевидно из кода.

## Что делать, если спецификация противоречит `ARCHITECTURE.md`

`ARCHITECTURE.md` — источник истины для контрактов. Если спецификация противоречит контракту — это баг спецификации, его надо исправить, а не подгонять контракт. Если противоречие внутри `DECISIONS.md` — обсудить с человеком, не решать молча.

## Что делать, если спецификация неполна

Если при написании кода обнаруживается, что спецификация чего-то не описывает (например, конкретный формат сообщения об ошибке), — **сначала зафиксировать решение в `DECISIONS.md`** (новый D-XX), потом писать код. Не решать молча: следующая итерация должна видеть, что решение было принято.

## Что дальше

После того как код написан и `tests/integration.md` проходит в режимах A и C (B — вручную) — проект готов к **шагу 17: живой сессии**. Протокол — в `LIVE_SESSION_PROTOCOL.md`. Три возможных исхода:

1. **Итерируем** — точечные правки канона, парсера, промпта; повтор шага 17.
2. **LLM не оправдывает сложности** — серьёзный разговор о том, нужна ли LLM на Уровне 1.
3. **Переход к Уровню 2** — LLM предлагает изменения состояния, движок валидирует и применяет. Архитектура готова к этому: точка расширения — между применением `applied` и вызовом сборщика промпта (`specs/session.md`, шаги 4–5).

## С чего начать прямо сейчас

1. Прочитай `README.md`, `ARCHITECTURE.md`, `DECISIONS.md`.
2. Прочитай `canon.yaml` и `templates.yaml`, чтобы понимать данные.
3. Начни с `specs/loaders.md`: напиши загрузчик канона, прогони `LD-1` (поставляемый канон загружается без ошибок), затем остальные тесты.
4. Переходи к `specs/projection.md`, затем к `specs/parser.md`, и так далее по порядку.
5. После `specs/engine.md` — прогони `E-A-1` (золотой путь в режиме `no-llm`). Это первый момент, когда можно проверить, что детерминированное ядро работает.
6. После `specs/interface.md` — прогони `tests/integration.md` целиком в режимах A и C.

Не начинай с LLM. Начинай с загрузчика и проекции.
