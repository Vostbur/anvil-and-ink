# Anvil and Ink

Текстовая приключенческая игра на архитектуре **«жёсткий движок + мягкий рассказчик»**, Уровень 1.

По состоянию на 2026-11-08:

- Шаги 1–11 из `ARCHITECTURE.md` §8 реализованы.
- Все автотесты зелёные (198 passed, 2 skipped по дизайну).
- Проведены три полные живые сессии (шаг 17).
- Режим `llm` работает на локальном Ollama (`qwen2.5:3b`, таймаут 30 с).
- Режим `no-llm` работает детерминированно без LLM.
- Решения D-76…D-84 зафиксированы в `DECISIONS.md`.
- Следующий шаг — агрегированная сводка по трём сессиям и выбор одного из трёх исходов.

---

## Идея проекта

Проект проверяет гипотезу:

> Можно ли сделать текстовую игру, где правда мира принадлежит детерминированному движку, а LLM используется только как рассказчик, не имеющий права менять состояние.

Ключевой принцип:

- Движок владеет состоянием, правилами, причинно-следственными кодами и проекцией мира.
- Парсер превращает ввод игрока в структурированную команду.
- Движок возвращает `Outcome`: успех/провал, причину и применённые примитивы.
- Проекция обновляет `GameState`.
- Сборщик промпта создаёт текст для LLM и манифест для валидатора.
- LLM может только описать уже произошедшее.
- Валидатор сверяет ответ LLM с манифестом (тем, что нарратор реально видел в промпте).
- Если LLM недоступен, отклонён или слишком медленный, игра деградирует до шаблонов.

LLM **не может**:

- добавить или убрать предмет;
- изменить флаг;
- переместить игрока;
- открыть дверь;
- придумать событие, которого нет в данных хода;
- изменить состояние мира.

## Основные контракты

Архитектура завязана на несколько сквозных типов. Подробные определения — в `ARCHITECTURE.md` §3.

### `Command`

Структурированная команда из парсера. Пример:

    verb: GO
    args:
      direction: east
    resolved:
      direction: true
    raw: "идти на восток"

Парсер не проверяет правила мира. Он только понимает ввод.

### `Outcome`

Результат применения команды движком:

- `result`: `ok` или `fail`;
- `reason_code`: машинная причина (например `locked`, `no_item_here`);
- `applied`: список примитивов изменения состояния;
- `response_text`: канонический текст из мира, если есть.

Движок — единственный источник правды о том, что произошло.

### `GameState`

Детерминированная проекция состояния:

- текущая локация;
- инвентарь `{item_id: count}`;
- флаги `{flag_id: bool}`;
- размещения предметов `{loc_id: {item_id: count}}`;
- размещения NPC `{npc_id: loc_id}`;
- статистика;
- номер хода.

### `Manifest`

Манифест для валидатора. Описывает, что нарратор видел в промпте:

- `allowed_names`: множество разрешённых имён/слов;
- `allowed_numbers`: множество разрешённых чисел;
- `mode`: `look` или `describe`;
- `verb`: глагол хода;
- `reason_code`: причина хода.

Валидатор сверяет ответ LLM с манифестом, а не с «истиной мира». Нарратор не должен знать того, чего ему не показывали (D-80).

### `TurnResult`

То, что получает игрок за ход: финальный текст, флаг завершения игры, флаг прерывания.

### `Event`

Запись для логов и save/load. Два вида:

- `turn`: сырая команда, распаршенная команда, исход движка;
- `presentation`: финальный текст и ступень лестницы (`rung`).

## Ступени рассказчика (`rung`)

| Значение | Смысл |
| --- | --- |
| `1` | Ответ LLM принят с первой попытки. |
| `2` | Первая попытка отклонена валидатором, вторая принята. |
| `3` | Использован шаблон fallback. |
| `null` | Команда `UNKNOWN`, LLM не вызывался. |
| `4` | Аварийная заглушка. В норме не должна появляться. |

Интерпретация:

- Много `rung=1` — LLM работает и справляется.
- Много `rung=2` — модель часто нарушает контракт (галлюцинации, числа, имена). Смотреть `diagnostic.jsonl`.
- Много `rung=3` — LLM недоступен, таймауты, или валидатор слишком агрессивен.
- `rung=4` — баг или крайне аварийная ситуация.

- `pytest` для тестов.

- Установленный Ollama (`ollama --version`).
- Модель `qwen2.5:3b` (по умолчанию, зашита в `OllamaClient`).

- Зависимость `httpx` **не требуется**: клиент работает через stdlib `urllib.request` (D-78).

## Как читать диагностику

Каждая запись в `diagnostic_*.jsonl` содержит:

- `turn`: номер хода;
- `rung`: ступень рассказчика;
- `skip_reason`: почему LLM не вызывался (`unknown_command`);
- `fallback_reason`: почему деградация (`timeout_twice`, `validation_failed_twice`);
- `final_text`: текст, который увидел игрок;
- `calls`: массив попыток LLM с промптом, ответом, латентностью, результатом валидатора.

### Сводка в конце сессии

Скрипт печатает:

    Ходов:            N
    UNKNOWN (rung=null): X
    LLM (rung=1):     Y
    Шаблон (rung=3):  Z
    Заглушка (rung=4):W
    Победа:           True/False
    Прервана:         True/False

### Ориентиры по метрикам

| Метрика | Хороший знак | Тревожный знак |
| --- | --- | --- |
| Доля `UNKNOWN` | < 10–15% | > 15–20% |
| `rung=1` | Большинство ходов | Почти нет |
| `rung=2` | Умеренно (1–2 на сессию) | Слишком много |
| `rung=3` | Редко | Почти все ходы |
| `rung=4` | Нет вообще | Появился хотя бы раз |
| Латентность | 5–20 с после прогрева | Стабильно > 30 с |
| Победа | Игрок дошёл без подсказок | Застрял или сдался |

### Частые диагнозы

**Много `timeout_or_network`:**

- Модель не прогрета → запустить `bench_ollama.py`.
- Модель слишком тяжёлая → взять `3b` вместо `7b`.
- Таймаут слишком низкий → `$env:ANVIL_LLM_TIMEOUT = "45"`.
- Старая переменная окружения перебивает дефолт → проверить `$env:ANVIL_LLM_TIMEOUT`.

**Много `validation_failed_twice`:**

- Модель галлюцинирует имена/числа → смотреть `calls[].validator_result` и `reject`-причины.
- Манифест не разрешает слова из промпта → правка `prompt_builder.py` (D-80, D-83).
- Промпт слишком свободный → ужесточить `_SYSTEM_TEMPLATE`.

**Много `UNKNOWN`:**

- Игрок пишет свободные вопросы → собирать формулировки, добавлять алиасы точечно.
- Парсер не покрывает морфологию → D-76 (стемминг + порог 75).
- Канон не подсказывает естественные действия → правка `description` (D-84).

## Результаты живых сессий (шаг 17)

### Сессия 1 (до D-80/D-81)

- Режим: `llm`, модель `qwen2.5:7b`, таймаут 10 с.
- 31 ход, 11 `UNKNOWN` (≈ 35%).
- Все обычные ходы `rung=3` (шаблон), потому что таймаут 10 с < латентность 20–50 с.
- Игрок прошёл без подсказок.
- Вывод: стенд не настроен, LLM не измерен.

### Сессия 2 (после D-80/D-81/D-82)

- Режим: `llm`, модель `qwen2.5:3b`, таймаут 20 с (старая env-переменная).
- 31 ход, 7 `UNKNOWN` (≈ 23%).
- Смесь `rung=1/2/3`. Несколько ложных таймаутов на 22 с.
- Игрок прошёл. Заметил галлюцинации («фляга пустая», «вы входите» при осмотре).
- Вывод: D-80 убрал ложные reject по числам/именам, но таймаут 20 с всё ещё резал ответы.

### Сессия 3 (после D-80…D-84)

- Режим: `llm`, модель `qwen2.5:3b`, таймаут 30 с (дефолт D-81).
- 22 ход, 2 `UNKNOWN` (≈ 9%).
- Подавляющее большинство `rung=1`, несколько `rung=2`, один `rung=3`.
- Игрок прошёл. Навигационные подсказки D-84 работали.
- Остаточные проблемы: `UNKNOWN` на «дать раненому флягу», «войти в бункер», «что у меня в инвентаре».
- Вывод: стенд настроен, данные по всем трём осям собраны.

## Известные ограничения MVP

### Парсер

Не является полноценной NLP-системой. Использует: нормализацию, точный longest match, fuzzy (rapidfuzz), стемминг (D-76), substring matching для `item`/`npc`/`target`/`topic` (D-82).

Не понимает (осознанно или пока):

- свободные вопросы: «где я?», «есть выход?», «куда идти?»
- двойной объект: «дать раненому флягу», «отдать флягу торговцу»
- цель вместо направления: «войти в бункер», «идти в бункер»
- команду инвентаря: «что у меня?», «инвентарь», «осмотреть вещи»

Часть решается алиасами и подсказками канона. Часть — граница Уровня 1.

### Валидатор

Консервативен (D-40). Проверяет: пустоту, длину, утечку механики, неизвестные числа, неизвестные канонные имена.

**Не проверяет смысл.** LLM может написать грамматически допустимый, но фабульно неверный текст:

- «вы входите» при `осмотреться`;
- «фляга пустая» при `взять флягу`;
- «источник тепла» в холодном мире;
- лишние atmospheric детали.

Это известное ограничение. Измеряется в живых сессиях через вопрос 7 пост-интервью.

### Команда инвентаря

Штатной команды просмотра инвентаря нет. Игроки пишут «что у меня?», «инвентарь», «осмотреть вещи» → `UNKNOWN`. В режиме `llm` модель иногда упоминает инвентарь в прозе (он есть в промпте), но это не гарантировано. Кандидат на расширение парсера или канона.

### LLM на CPU

На 16 ГБ RAM без GPU:

- Первый вызов: 30–50 с (загрузка модели).
- Последующие: 7–20 с.
- При таймауте 30 с ложных отказов почти нет.
- Игрок ждёт 10–20 с на ход. Приемлемо для короткой игры, но не для длинной.

### Шаблоны

Обеспечивают играбельность без LLM. Суше и механистичнее. Задача — не заменить автора, а гарантировать, что игра не ломается.

## Что делать после живой сессии

Протокол подробно описан в `LIVE_SESSION_PROTOCOL.md`. Кратко:

1. Сохранить транскрипт, сейв, диагностику.
2. Записать наблюдения ведущего: паузы >15 с, повторы, опечатки, реакции, догадки.
3. Провести пост-интервью (7 вопросов: 5 общих + 2 про LLM).
4. Посчитать метрики: доля `UNKNOWN`, распределение `rung`, латентность, fallback-причины.
5. Разложить находки по категориям: баг / пробел канона / пробел парсера / ограничение MVP.
6. Точечные правки. Не редизайн.
7. Повторить с новым игроком.

Минимум три сессии перед существенными изменениями. Один прогон — не данные.

## Расширение канона

Подробная инструкция — в `CANON_AUTHORING.md`. Кратко:

1. Нарисовать граф мира (локации, связи, предметы, NPC, флаги, победа).
2. Заполнить `meta`, `initial_state`, `flags`.
3. Добавить локации с `description` (навигационные подсказки через `;`), `exits`, `entities`.
4. Добавить предметы с `takeable`, `use`-правилами.
5. Добавить NPC с темами (`key`, `response`, `condition`, `effects`).
6. Добавить `use_targets` для дверей/механизмов.
7. Проверить `verbs`, `directions`, `reason_codes`.
8. Обновить `templates.yaml`.
9. Прогнать `no-llm` вручную.
10. Прогнать негативные сценарии.
11. Только потом включать `llm`.
12. Запустить `pytest -q`.

## Дальнейшее развитие

Текущий уровень — Уровень 1: жёсткий движок + мягкий рассказчик.

Возможные направления после агрегированной сводки:

1. Точечное расширение канона по находкам сессий.
2. Улучшение парсера по реальным формулировкам (алиасы, возможно `INVENTORY`).
3. Улучшение промпта и валидатора (смысловые проверки, если данные покажут необходимость).
4. Переход к Уровню 2: LLM предлагает структурированные изменения состояния, движок валидирует и применяет. Точка расширения — между `applied` и сборщиком промпта (`specs/session.md`, шаги 4–5).

Переход к Уровню 2 — не автоматический следующий шаг. Оправдан только если живые сессии покажут, что мир слишком закрыт и никакие подсказки не решают проблему.
