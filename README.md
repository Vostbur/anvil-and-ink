# Anvil and Ink

Текстовая приключенческая игра на архитектуре **«жёсткий движок + мягкий рассказчик»**, Уровень 1.

По состоянию на 2026-11-08:

- Шаги 1–11 из `ARCHITECTURE.md` §8 реализованы.
- Автоматические тесты зелёные.
- Живой стенд для шага 17 настроен: Ollama, модель `qwen2.5:3b`, таймаут по умолчанию 30 секунд.
- Проведены две полные живые сессии и несколько микропроверок.
- Перед существенным редизайном по протоколу желательно провести третью живую сессию.
- Режим `llm` требует локального Ollama. Режим `no-llm` работает детерминированно без LLM.

---

## Идея проекта

Проект проверяет гипотезу:

> Можно ли сделать текстовую игру, где правда мира принадлежит детерминированному движку, а LLM используется только как рассказчик, не имеющий права менять состояние.

Ключевой принцип:

- Движок владеет состоянием, правилами, причинно-следственными кодами и проекцией мира.
- Парсер превращает ввод игрока в структурированную команду.
- Движок возвращает `Outcome`: успех/провал, причину и применённые примитивы.
- Проекция обновляет `GameState`.
- Сборщик промпта создаёт текст для LLM и манифест для валидатора.
- LLM может только описать уже произошедшее.
- Валидатор сверяет ответ LLM с манифестом, то есть с тем, что нарратор реально видел.
- Если LLM недоступен, отклонён или слишком медленный, игра деградирует до шаблонов.

LLM не может:

- добавить предмет;
- убрать предмет;
- изменить флаг;
- переместить игрока;
- открыть дверь;
- придумать событие, которого нет в данных хода;
- изменить состояние мира.

## Основные контракты

Архитектура завязана на несколько сквозных типов.

### `Command`

Структурированная команда, которую вернул парсер.

Пример смыслового содержания:

    verb: GO
    args:
      direction: east
    resolved:
      direction: true
    raw: "идти на восток"

Парсер не проверяет правила мира. Он только понимает ввод.

### `Outcome`

Результат применения команды движком.

Содержит:

- `result`: `ok` или `fail`;
- `reason_code`: машинная причина;
- `applied`: список примитивов изменения состояния;
- `response_text`: канонический текст из мира, если есть.

Движок — единственный источник правды о том, что произошло.

### `GameState`

Детерминированная проекция состояния игры:

- текущая локация;
- инвентарь;
- флаги;
- размещения предметов;
- размещения NPC;
- номер хода;
- статистика, если используется.

### `Manifest`

Манифест для валидатора. Он описывает, что нарратор видел в промпте:

- разрешённые имена;
- разрешённые числа;
- режим описания;
- глагол;
- причину хода.

Валидатор сверяет ответ LLM не с «объективной истиной мира», а с манифестом. Это важно: нарратор не должен знать того, чего ему не показывали.

### `TurnResult`

То, что получает игрок за ход:

- финальный текст;
- завершена ли игра;
- прервана ли сессия;
- причина прерывания, если была.

### `Event`

Запись для логов и save/load. Обычно бывает двух видов:

- `turn`: сырая команда, распаршенная команда, исход движка;
- `presentation`: финальный текст и ступень лестницы.

## Ступени рассказчика

В диагностики и событиях используется поле `rung`.

| Значение | Смысл |
| --- | --- |
| `1` | Ответ LLM принят с первой попытки. |
| `2` | Первая попытка LLM отклонена, вторая принята. |
| `3` | Использован шаблон fallback. |
| `null` | Команда `UNKNOWN`, LLM не вызывался. |
| `4` | Аварийная заглушка. В норме не должна появляться. |

Если в живой сессии появляется много `rung=3`, это может означать:

- LLM недоступен;
- таймауты;
- валидатор слишком агрессивно отклоняет ответы;
- модель не справляется с форматом;
- канон/промпт дают модели противоречивые данные.

Если появляется `rung=4`, это баг или крайне аварийная ситуация.

## Режимы сессии

| Режим | Назначение |
| --- | --- |
| `no-llm` | Детерминированная игра через шаблоны. Хорош для проверки парсера, канона и механики. |
| `llm` | Живая игра с Ollama. Проверяет нарратора. |
| `broken-llm` | Тестовый режим с инжекцией отказов LLM. Используется в интеграционных тестах. |

Для ручной проверки без LLM:

    python scripts/live_session.py --mode no-llm

Для живой сессии с LLM:

    python scripts/live_session.py --mode llm

## Требования

### Минимальные для `no-llm`

- Python 3.11 или новее. Проект тестировался на Python 3.13.
- Зависимости из `pyproject.toml`.
- `pytest` для тестов.
- `rapidfuzz` для устойчивого парсинга русских форм.

### Дополнительные для `llm`

- Установленный Ollama.
- Локальная модель. По умолчанию используется `qwen2.5:3b`.
- Достаточно памяти. На CPU с 16 ГБ модель работает, но первый вызов может быть медленным.
- Желательно прогреть модель перед сессией.

## Установка с нуля

Ниже — вариант для Windows PowerShell. Для Linux/macOS команды activation и пути отличаются, но суть та же.

### 1. Клонировать репозиторий

    git clone <url-репозитория>
    cd anvil-and-ink

### 2. Создать виртуальное окружение

    python -m venv .venv

### 3. Активировать окружение

Windows PowerShell:

    .venv\Scripts\Activate.ps1

Если PowerShell блокирует скрипты, временно разрешите для текущего окна:

    Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass

Затем снова:

    .venv\Scripts\Activate.ps1

Linux/macOS:

    source .venv/bin/activate

### 4. Установить проект

Если в `pyproject.toml` уже объяжены зависимости:

    python -m pip install --upgrade pip
    pip install -e .

Для тестов и парсера желательно убедиться, что установлены:

    pip install pytest rapidfuzz PyYAML

Если в проекте есть extra-зависимости для разработки, можно попробовать:

    pip install -e ".[dev]"

### 5. Проверить автотесты

    pytest -q

Ожидаемый результат: все тесты зелёные, кроме пропусков, которые явно отмечены в спецификациях.

Быстрая проверка ключевого интеграционного теста:

    pytest tests/test_integration.py::test_e_a_1_golden_path_no_llm -v

## Запуск Ollama

### 1. Убедиться, что Ollama установлен

    ollama --version

### 2. Запустить сервер Ollama

В отдельном терминале:

    ollama serve

Обычно Ollama поднимает локальный сервер на:

    http://localhost:11434

### 3. Проверить список моделей

    ollama list

### 4. Скачать модель по умолчанию

    ollama pull qwen2.5:3b

В проекте по умолчанию зафиксированы:

- модель: `qwen2.5:3b`;
- base URL: `http://localhost:11434`;
- таймаут: 30 секунд.

Эти значения уже вшиты в `OllamaClient`. Переменные окружения нужны только если хочется переопределить поведение.

## Прогрев модели перед живой сессией

Первый вызов LLM может быть медленным, потому что модель загружается в память. Перед настоящей сессией лучше прогреть модель:

    python bench_ollama.py

Ожидаемый признак готовности: после первого медленного вызова следующие вызовы дают `ok=True` и разумную латентность, например 7–20 секунд на CPU.

Если модель постоянно отвечает дольше 30 секунд, можно временно увеличить таймаут:

    $env:ANVIL_LLM_TIMEOUT = "45"

или:

    $env:ANVIL_LLM_TIMEOUT = "60"

Но для живой сессии лучше не гонять слишком медленную модель: игрок не должен ждать полминуты каждый ход.

## Запуск игры

### Детерминированный режим без LLM

    python scripts/live_session.py --mode no-llm

Этот режим полезен для проверки:

- понимает ли парсер команды;
- проходима ли игра;
- достаточно ли подсказок в каноне;
- корректно ли работают шаблоны;
- не сломана ли механика.

### Живой режим с LLM

Сначала прогрев:

    python bench_ollama.py

Затем:

    python scripts/live_session.py --mode llm

Этот режим проверяет:

- качество прозы LLM;
- поведение лестницы;
- частоту fallback на шаблоны;
- влияние LLM на вовлечённость.

### Запуск с другим каноном

    python scripts/live_session.py --mode no-llm --canon my_world.canon.yaml --templates my_world.templates.yaml

Для LLM:

    python scripts/live_session.py --mode llm --canon my_world.canon.yaml --templates my_world.templates.yaml

Подробнее о создании канона — в `CANON_AUTHORING.md`.

## Как читать диагностику

В `diagnostic_*.jsonl` каждая запись обычно содержит:

- `turn`: номер хода;
- `rung`: ступень рассказчика;
- `skip_reason`: почему LLM не вызывался, например `unknown_command`;
- `fallback_reason`: почему произошла деградация, например `timeout_twice` или `validation_failed_twice`;
- `final_text`: текст, который увидел игрок;
- `calls`: попытки LLM с промптами, ответами, латентностью и результатом валидатора.

### Полезные метрики после сессии

Скрипт в конце печатает сводку. Ориентиры:

| Метрика | Хороший знак | Тревожный знак |
| --- | --- | --- |
| Доля `UNKNOWN` | меньше 10–15% | больше 15–20% |
| `rung=1` | много | почти нет |
| `rung=2` | умеренно | слишком много |
| `rung=3` | редко или как fallback | почти все ходы |
| `rung=4` | нет | появился хотя бы раз |
| Латентность | 5–20 секунд после прогрева | стабильно больше 30 секунд |
| Победа | игрок дошёл без подсказок | игрок застрял или сломался |

### Частые диагнозы

#### Много `timeout_or_network`

Вероятные причины:

- модель не прогрета;
- модель слишком тяжёлая для CPU;
- таймаут слишком низкий;
- Ollama перегружен;
- длинный промпт и много токенов.

Что делать:

- запустить `bench_ollama.py`;
- увеличить `ANVIL_LLM_TIMEOUT`;
- взять модель легче;
- сократить `max_tokens`;
- уменьшить историю в промпте, если это предусмотрено конфигом.

#### Много `validation_failed_twice`

Вероятные причины:

- модель галлюцинирует имена/числа;
- манифест не разрешает слова, которые модель видела в промпте;
- промпт слишком свободный;
- шаблонный fallback лучше, чем LLM, потому что LLM не держит контракт.

Что делать:

- смотреть `calls` в диагностике;
- сверять `validator_result`;
- править промпт, манифест или валидатор;
- проверять, не противоречат ли данные хода друг другу.

#### Много `UNKNOWN`

Вероятные причины:

- игрок пишет свободные вопросы;
- парсер не знает нужные глаголы/предлоги;
- канон не подсказывает естественные действия;
- русская морфология не покрывается эвристикой.

Что делать:

- собирать реальные формулировки игроков;
- добавлять алиасы только для частых паттернов;
- править описания локаций и NPC, чтобы направлять игрока;
- не переписывать парсер после одной сессии.

## Известные ограничения MVP

### Парсер

Парсер не является полноценной NLP-системой. Он использует:

- нормализацию;
- точный longest match по алиасам;
- fuzzy match;
- стемминг для русских падежных форм;
- substring matching для предметов, NPC, целей и тем.

Он хорошо понимает близкие к канону команды, но может не понимать свободные вопросы:

    где я?
    есть выход?
    что у меня в инвентаре?
    дать раненому флягу
    войти в бункер

Часть этих проблем решается алиасами и подсказками канона. Часть — это осознанное ограничение Уровня 1.

### Валидатор

Валидатор консервативен. Он проверяет:

- пустоту;
- длину;
- утечку механики;
- неизвестные числа;
- неизвестные канонные имена.

Он не проверяет смысл. Поэтому LLM может написать грамматически допустимый, но фабульно неверный текст:

- «вы входите» там, где игрок просто осмотрелся;
- «фляга пустая», хотя игрок только взял её;
- «источник тепла» в холодном мире;
- лишние atmospheric детали, которых нет в данных.

Это известное ограничение. Оно измеряется в живых сессиях через пост-интервью и чтение транскриптов.

### LLM на CPU

На слабом железе даже маленькая модель может быть медленной. Для живой сессии критично не только качество, но и задержка. Игрок не должен ждать полминуты каждый ход.

Поэтому в проекте зафиксирован компромисс:

- `qwen2.5:3b` как дефолт;
- таймаут 30 секунд;
- обязательный прогрев перед сессией;
- fallback на шаблоны.

### Шаблоны

Шаблоны обеспечивают играбельность без LLM, но они суше и механистичнее. Их задача — не заменить хорошего автора, а гарантировать, что игра не ломается, когда LLM недоступен.

## Что делать после живой сессии

Протокол описан в `LIVE_SESSION_PROTOCOL.md`. Кратко:

1. Сохранить транскрипт, сейв и диагностику.
2. Записать наблюдения ведущего:
   - паузы;
   - повторы;
   - опечатки;
   - реакции;
   - моменты догадки.
3. Провести пост-интервью:
   - что происходило;
   - что было непонятно;
   - что понравилось;
   - что раздражало;
   - одну вещь поменять;
   - заметна ли смена стиля;
   - были ли моменты, когда текст говорил не то, что происходило.
4. Посчитать объективные метрики:
   - доля `UNKNOWN`;
   - распределение `rung`;
   - латентность;
   - fallback-причины.
5. Разложить находки по категориям:
   - баг;
   - пробел канона;
   - пробел парсера;
   - ограничение MVP.
6. Сделать только точечные правки.
7. Повторить сессию с новым игроком.

Существенные изменения запускаются только после минимум трёх сессий, если находка не является объективным багом.

## Ключевые решения, влияющие на эксплуатацию

В `DECISIONS.md` есть записи, важные для запуска и правок:

- D-76: парсер использует стемминг и сниженный порог для пословного матча.
- D-80: манифест разрешает числа и слова, которые реально присутствуют в промпте, кроме служебных номеров ходов.
- D-81: дефолтный LLM-клиент — `qwen2.5:3b`, таймаут 30 секунд.
- D-82: темы `TALK` участвуют в substring matching.
- D-83: слова из описания локации попадают в разрешённые имена манифеста.
- D-84: описания локаций содержат навигационные подсказки.

Эти решения делают живой стенд честным: валидатор не должен наказывать модель за то, что модель видела в промпте.

## Дальнейшее развитие

Текущий уровень — Уровень 1: жёсткий движок + мягкий рассказчик.

Возможные направления после живых сессий:

1. Точечное расширение канона.
2. Улучшение парсера по реальным формулировкам игроков.
3. Улучшение промпта и валидатора.
4. Переход к Уровню 2, где LLM может предлагать структурированные изменения состояния, а движок их валидирует и применяет.

Переход к Уровню 2 — не автоматический следующий шаг. Он оправдан только если живые сессии покажут, что мир слишком закрыт для игрока и никакие канонические подсказки не решают проблему.
